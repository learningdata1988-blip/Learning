Key Concepts

1. Managed Location

  • Kya hota hai: Yeh ek aisi storage location hoti hai jise Databricks ya Spark khud poori tarah manage karta hai.
  • Simple bhasha: Agar aapne managed table banayi aur usko drop kar diya, toh uska data aur metadata dono storage se permanently delete ho jayenge.

2. External Location

  • Kya hota hai: Yeh aapki khud ki cloud storage (jaise AWS S3 bucket ya Azure ADLS) hoti hai jise aap Spark/Databricks se connect karte ho.
  • Simple bhasha: Agar aapne external table drop ki, toh sirf table ka reference (metadata) khatam hota hai, lekin asli data aapke cloud storage mein safe rehta hai.

3. Data Lake

  • Kya hota hai: Ek bohot bada centralized storage system jahan aap har tarah ka data—chahe wo structured ho (CSV, Parquet) ya unstructured (audio, video, logs)—ek hi jagah raw form mein store kar sakte hain.

4. Delta Lake

  • Kya hota hai: Yeh Data Lake ke upar ki ek storage layer hai jo Apache Parquet files ke sath milti-julti hai, par ismein ACID transactions (reliability), Time Travel (purana data dekhna), aur data validation jaisi advanced features milti hain.

5. Delta Table

  • Kya hota hai: Delta Lake format ke andar bani hui table jo rows aur columns mein data rakhti hai aur reliable updates/deletes support karti hai.

6. Spark Manager (Driver Node)

  • Kya hota hai: Spark cluster ka "Boss" ya coordinator.
  • Simple bhasha: Jab aap code likhte ho, toh Driver us code ko samajhta hai, chote-chote tasks mein todta hai, aur Worker nodes ko kaam assign karta hai. Poora application yahi control karta hai.

7. Worker Nodes

  • Kya hota hai: Spark cluster ke "Laborers" ya workers jo actual heavy lifting (data processing aur calculations) karte hain. Driver inhi nodes ko kaam bhejta hai.

8. Shuffling

  • Kya hota hai: Jab data ko alag-alag worker nodes ke beech network ke through transfer karna padta hai.
  • Simple bhasha: Jaise aap groupBy ya join operation chalate ho, toh ek hi key ka data alag nodes se ek jagah ikattha karna padta hai—is process ko shuffling kehte hain, aur yeh network par thoda heavy padta hai.

9. Reshuffling

  • Kya hota hai: Jab data ka distribution theek nahi hota (kisi node par bohot zyada data aur kisi par kam), toh Spark data ko dobara se re-partition karke nodes par barabar batata hai taaki performance behtar ho sake.

10. Lazy Evaluation

  • Kya hota hai: Spark ki ek smart aadat. Jab aap transformations (jaise .filter(), .select()) likhte ho, toh Spark turant run nahi karta. Wo bas ek plan banakar chupchap baith jata hai. Jab tak aap koi Action (jaise .show(), .count()) trigger nahi karoge, tab tak Spark kuch execute nahi karega.

11. Temporary Views

  • Kya hota hai: Ek virtual table jo sirf uss specific Spark session ke andar hi zinda rehti hai. Ispe aap SQL queries chala sakte hain bina permanent storage par table banaye. Session band hote hi view gayab ho jata hai.

Key Concepts – Part 2

1. Partitioning and Z-Ordering

  • Partitioning: Jab data bohot bada hota hai, toh usko chote-chote folders (jaise Year=2024/Month=10) mein tod kar rakha jata hai. Isse Spark ko poora data scan nahi karna padta, bas sahi folder se data read ho jata hai.
  • Z-Ordering: Yeh Delta Lake ki ek technique hai jo ek hi partition ke andar multiple columns par data ko is tarah arrange karti hai ki search queries bohot fast ho jayein.

2. Broadcast Joins / MapSide Joins

  • Kya hota hai: Jab aap ek bohot badi table ko ek bohot choti table ke sath join karte ho, toh Spark choti table ki ek copy har Worker node par bhej (broadcast kar) deta hai.
  • Fayda: Isse heavy data transfer (shuffling) ki zaroorat nahi padti aur join search fast ho jata hai.

3. Spark UI & Performance Tuning

  • Spark UI: Ek web-based dashboard jahan aap dekh sakte hain ki aapka Spark code kaise run ho raha hai, kahan time lag raha hai, aur kaun sa node slow chal raha hai.
  • Performance Tuning: Code ya cluster settings ko optimize karna (jaise memory settings, partition sizes adjust karna) taaki queries kam cost aur fast time mein execute ho sakein.

4. Time Travel & Vacuum Command in Delta

  • Time Travel: Delta Lake mein jab aap data update ya delete karte ho, toh purana data gayab nahi hota. Aap past ki kisi specific date/version par jaakar purana data wapas dekh sakte ho.
  • Vacuum Command: Time travel ki wajah se purani files storage mein space gherne lagti hain. VACUUM command run karke hum un purani, unneeded files ko storage se permanently delete karte hain space free karne ke liye.

5. Caching & Persistence (cache() vs persist())

  • Kya hota hai: Agar aap ek hi intermediate dataframe ko baar-baar use kar rahe ho, toh usko RAM mein save kar lena taaki Spark ko har baar dobara calculation na karni pade.
  • Difference:
    • cache() -> Data ko default memory (RAM) mein save karta hai.
    • persist() -> Aapko option deta hai ki data RAM mein save karna hai, disk par save karna hai, ya dono par.

6. Catalyst Optimizer & Tungsten Engine

  • Catalyst Optimizer: Spark ka "Brain". Jab aap code likhte ho, toh yeh optimizer aapke code ka sabse efficient aur fastest execution plan banata hai.
  • Tungsten Engine: Spark ka "Engine". Yeh memory allocation aur hardware performance ko boost karke low-level code execution speed ko bohot fast kar deta hai.

7. Structured Streaming

  • Kya hota hai: Jab data batch mein nahi, balki real-time (stream wise) aata rehta hai—jaise credit card fraud detection, live transactions, ya IoT sensors.
  • Fayda: Spark same DataFrame APIs ka use karke is live data ko bina rukawat process karta chalta hai.

8. Delta Lake Lakehouse Architecture (Medallion Architecture)

Data ko clean aur high quality banane ke liye 3 layers mein organize kiya jata hai:

  • Bronze Layer (Raw Data): Jaise hi external source se data aata hai, waisa hi bina transform kiye yahan save hota hai.
  • Silver Layer (Cleaned Data): Bronze data se duplicates, null values hatakar aur joins/filtering karke thoda clean data yahan rakha jata hai.
  • Gold Layer (Business Data): Business reporting aur analytics ke liye aggregate kiya hua super-clean data, jise direct dashboards (PowerBI, Tableau) connect kar sakte hain

1.1SparkSession Initialization & Config

from pyspark.sql import SparkSession

spark = (
    SparkSession.builder
    .appName("orders-etl")
    .config("spark.sql.shuffle.partitions", "200")        # tune to data size
    .config("spark.sql.adaptive.enabled", "true")         # AQE (default in 3.2+)
    .config("spark.sql.adaptive.skewJoin.enabled", "true")
    .config("spark.sql.sources.partitionOverwriteMode", "dynamic")
    .config("spark.sql.session.timeZone", "UTC")
    .getOrCreate()
)

spark.sparkContext.setLogLevel("WARN")
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", 50 * 1024 * 1024)  # 50 MB

Best practices

  • Set cluster-level settings (executor memory/cores, dynamic allocation) at submit time; SQL settings can change at runtime with spark.conf.set.
  • Always use getOrCreate(); avoid multiple sessions unless isolating temp views via spark.newSession().
  • Pin timezone to UTC to avoid silent timestamp shifts between environments.
  • Keep config out of code: pass via --conf or environment-specific files.
  • Always spark.stop() in standalone scripts (not needed on Databricks).

1.2Lazy Evaluation, Transformations & Actions

Transformations only build a plan. Nothing runs until an action is called, which lets Spark optimize the whole pipeline.

TypeExamplesShuffle?
Narrowselect, filter, withColumn, map, union, coalesceNo – each output partition depends on one input partition; pipelined in one stage
WidegroupBy, join, distinct, orderBy, repartition, window with partitionByYes – data moves across the network; new stage
Actioncount, collect, show, take, write.*, foreachTriggers a job

Catalyst Optimizer pipeline

  1. Analysis – resolve columns/tables against the catalog.
  2. Logical optimization – predicate pushdown, column pruning, constant folding, join reordering.
  3. Physical planning – choose strategies (broadcast vs. sort-merge), cost-based.
  4. Code generation – Tungsten whole-stage codegen produces JVM bytecode.
df = (spark.read.parquet("/data/orders")
        .filter("order_date >= '2026-01-01'")   # pushed down to Parquet scan
        .select("order_id", "customer_id", "amount"))

df.explain(mode="formatted")   # physical plan; also "extended", "cost", "codegen"
df.count()                     # action: only now does work happen
TipRead the plan bottom-up. Look for PushedFilters, BroadcastHashJoin vs SortMergeJoin, and Exchange nodes (each is a shuffle).

2.1Columns, Filtering, Selection & Renaming

from pyspark.sql import functions as F

df2 = (df
    .select("order_id", "customer_id", F.col("amount").alias("order_amount"), "created_at")
    .withColumn("amount_usd", F.round(F.col("order_amount") * F.lit(1.0), 2))
    .withColumn("order_date", F.to_date("created_at"))
    .withColumn("size", F.when(F.col("order_amount") >= 1000, "large")
                         .when(F.col("order_amount") >= 100,  "medium")
                         .otherwise("small"))
    .withColumnRenamed("customer_id", "cust_id")
    .drop("created_at"))

# Rename many columns at once
df2 = df2.toDF(*[c.lower().replace(" ", "_") for c in df2.columns])

# filter == where
active = df2.filter((F.col("order_amount") > 50) & F.col("size").isin("medium", "large"))
active = df2.where("order_amount > 50 AND size IN ('medium','large')")   # SQL string form

# Useful expressions
df2.selectExpr("order_id", "order_amount * 1.1 AS with_tax")
df2.filter(F.col("order_id").like("A%") | F.col("cust_id").isNull())
df2.withColumns({"year": F.year("order_date"), "month": F.month("order_date")})  # Spark 3.3+
TipUse &, |, ~ with parentheses around each condition – Python's and/or/not will raise errors. Prefer one select with many expressions over a long chain of withColumn calls on wide tables.

2.2Joins: Broadcast vs. Sort-Merge

# join types: inner, left, right, full (outer), left_semi, left_anti, cross
joined = orders.join(customers, on="cust_id", how="left")

# Different column names -> explicit condition (alias to avoid ambiguity)
o, c = orders.alias("o"), customers.alias("c")
joined = o.join(c, F.col("o.cust_id") == F.col("c.id"), "inner").select("o.*", "c.name")

# Anti join: customers with NO orders
no_orders = customers.join(orders, customers.id == orders.cust_id, "left_anti")

3Window Functions

Windows compute a value per row using a related set of rows without collapsing them (unlike groupBy).

from pyspark.sql import Window
from pyspark.sql import functions as F

w = Window.partitionBy("cust_id").orderBy(F.col("created_at").desc())

ranked = (orders
    .withColumn("rn",    F.row_number().over(w))   # 1,2,3,4 – unique
    .withColumn("rk",    F.rank().over(w))         # 1,1,3,4 – gaps after ties
    .withColumn("drk",   F.dense_rank().over(w))   # 1,1,2,3 – no gaps
    .withColumn("prev",  F.lag("amount", 1).over(w))
    .withColumn("next",  F.lead("amount", 1, 0).over(w)))   # default 0 instead of null

# Classic: latest record per key
latest = ranked.filter("rn = 1").drop("rn", "rk", "drk", "prev", "next")

Frames: running totals & moving averages

w_run = (Window.partitionBy("cust_id").orderBy("created_at")
               .rowsBetween(Window.unboundedPreceding, Window.currentRow))
w_7   = (Window.partitionBy("cust_id").orderBy("created_at").rowsBetween(-6, 0))

orders = (orders
    .withColumn("running_total", F.sum("amount").over(w_run))
    .withColumn("moving_avg_7",  F.avg("amount").over(w_7))
    .withColumn("pct_of_cust",   F.col("amount") / F.sum("amount").over(Window.partitionBy("cust_id")))
    .withColumn("days_since_prev",
                F.datediff("created_at", F.lag("created_at").over(Window.partitionBy("cust_id").orderBy("created_at")))))
FunctionTiesTypical use
row_numberArbitrary but uniqueDedup / latest row
rankSame rank, gaps followCompetition ranking
dense_rankSame rank, no gapsTop-N levels
lag / leadn/aChange vs. previous period, sessionization
PerformanceA window without partitionBy moves all data to a single partition. Always partition, and add a deterministic tie-breaker to orderBy when using row_number.

3.1Missing Data & Deduplication

# Drop rows
df.dropna()                                   # any null in any column
df.dropna(how="all")                          # only if all columns null
df.dropna(subset=["order_id", "amount"])      # required columns
df.dropna(thresh=3)                           # keep rows with >= 3 non-null values

# Fill
df.fillna(0, subset=["amount"])
df.fillna({"amount": 0.0, "region": "UNKNOWN"})
df.withColumn("amount", F.coalesce("amount", F.lit(0)))   # column-wise fallback chain

# NaN is not NULL for floats
df.filter(~F.isnan("amount") & F.col("amount").isNotNull())

# Dedup
df.distinct()                                 # full-row
df.dropDuplicates(["order_id"])               # by key – which row survives is NOT deterministic

# Deterministic dedup: keep latest per key
w = Window.partitionBy("order_id").orderBy(F.col("updated_at").desc())
dedup = df.withColumn("rn", F.row_number().over(w)).filter("rn = 1").drop("rn")
TipFor streaming, dropDuplicates needs a watermark (withWatermark) or state grows forever.

# Config
spark.conf.set("spark.sql.shuffle.partitions", 400)      # default 200
spark.conf.set("spark.sql.files.maxPartitionBytes", 128 * 1024 * 1024)
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", True)   # AQE merges small shuffle partitions

Rules of thumb

  • Target 100–200 MB per partition and 2–4 tasks per CPU core.
  • Too few partitions → idle cores, OOM/spills. Too many → scheduler overhead, small files.
  • Filter and select before joins/aggregations to shrink shuffled data.
  • Enable AQE: it coalesces partitions, switches to broadcast at runtime, and splits skewed partitions.
  • Use the Spark UI → Stages tab: watch Shuffle Read/Write, Spill and the task duration spread.

4.1Caching & Persistence

Cache a DataFrame only when it is reused by multiple actions and is expensive to recompute.

from pyspark import StorageLevel

clean = raw.filter("amount > 0").join(broadcast(dim), "id")

clean.cache()                                   # = persist(MEMORY_AND_DISK) for DataFrames
clean.persist(StorageLevel.MEMORY_AND_DISK_DESER)
clean.count()                                   # cache is lazy – materialize with an action

clean.groupBy("region").count().show()          # reuses cache
clean.agg(F.sum("amount")).show()               # reuses cache

clean.unpersist()                               # free memory when done
spark.catalog.clearCache()
Storage levelBehaviour
MEMORY_ONLYFastest; partitions that don't fit are recomputed
MEMORY_AND_DISKSpills to disk instead of recomputing (DataFrame default)
DISK_ONLYSlow but safe for large reusable data
*_2 suffixReplicated on two nodes (fault tolerance)
OFF_HEAPAvoids GC pressure; requires off-heap memory config
WarningCaching a DataFrame that is used once wastes memory. For very long lineages (iterative jobs) prefer df.checkpoint() to truncate the plan.

4.2Avoiding Common Bottlenecks

Data skew

Symptom: one task runs far longer than the rest in the Spark UI. Cause: hot keys (e.g. NULL, "unknown", a mega-customer).

# 1) Let AQE split skewed partitions (Spark 3+)
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", True)

# 2) Salting: spread a hot key across N buckets
N = 16
big   = big.withColumn("salt", (F.rand() * N).cast("int"))
small = small.withColumn("salt", F.explode(F.array([F.lit(i) for i in range(N)])))
joined = big.join(small, ["key", "salt"]).drop("salt")

# 3) Isolate hot keys: broadcast-join them separately, sort-merge the rest
# 4) Filter junk keys (NULLs) before the join

Excessive shuffles

  • Chain operations that share a partitioning key; avoid repeated repartition and orderBy (a global sort is a shuffle – sort only at the end if needed).
  • Prefer reduceByKey-style aggregations (groupBy().agg()) over collect_list + Python processing.
  • Pre-bucket large tables joined often: df.write.bucketBy(64, "cust_id").sortBy("cust_id").saveAsTable("t") removes shuffles at join time.

UDF overhead

# Slowest: Python UDF – row-by-row serialization, opaque to Catalyst
@F.udf("string")
def clean_slow(s):
    return s.strip().lower() if s else None

# Better: built-in functions (optimized, codegen)
df.withColumn("name", F.lower(F.trim("name")))

# If custom logic is unavoidable: pandas (vectorized) UDF with Arrow
import pandas as pd
from pyspark.sql.functions import pandas_udf

@pandas_udf("double")
def zscore(s: pd.Series) -> pd.Series:
    return (s - s.mean()) / s.std()

df.withColumn("z", zscore("amount"))

result = spark.sql("""
    WITH monthly AS (
        SELECT cust_id,
               date_trunc('month', created_at) AS month,

7Upsert (MERGE) with Delta Lake

An upsert updates rows that already exist in the target and inserts those that don't. Delta's MERGE does this atomically (ACID), so readers never see a half-applied batch.

Python API

from delta.tables import DeltaTable
from pyspark.sql import Window, functions as F

# 1) ALWAYS dedupe the source: MERGE fails if multiple source rows match one target row
w = Window.partitionBy("order_id").orderBy(F.col("updated_at").desc())
updates = (raw_updates.withColumn("rn", F.row_number().over(w))
                      .filter("rn = 1").drop("rn"))

target = DeltaTable.forName(spark, "silver.orders")        # or forPath(spark, "/lake/silver/orders")

(target.alias("t")
   .merge(updates.alias("s"), "t.order_id = s.order_id")
   .whenMatchedUpdate(
        condition="s.updated_at > t.updated_at",               # only newer versions win; skips no-op writes
        set={"amount": "s.amount", "status": "s.status", "updated_at": "s.updated_at"})
   .whenMatchedDelete(condition="s.is_deleted = true")        # propagate deletes (CDC)
   .whenNotMatchedInsertAll()
   .execute())

SQL form

updates.createOrReplaceTempView("updates")

MERGE INTO silver.orders AS t
USING updates AS s
  ON t.order_id = s.order_id
WHEN MATCHED AND s.is_deleted = true THEN DELETE
WHEN MATCHED AND s.updated_at > t.updated_at THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

Upsert on plain Parquet (no Delta)

7.2SCD Type 2 – Full History

Each change closes the current row (sets an end date, is_current = false) and inserts a new row. You can then query the dimension "as of" any date.

Target table

CREATE TABLE IF NOT EXISTS gold.dim_customer_scd2 (
  customer_sk    BIGINT GENERATED ALWAYS AS IDENTITY,   -- surrogate key (Delta identity column)
  customer_id    BIGINT,                                -- business key
  name           STRING,
  email          STRING,
  city           STRING,
  row_hash       STRING,
  effective_from TIMESTAMP,
  effective_to   TIMESTAMP,                             -- NULL = still open
  is_current     BOOLEAN
) USING DELTA;

Single-MERGE pattern (close old + insert new)

from delta.tables import DeltaTable
from pyspark.sql import functions as F

dim = DeltaTable.forName(spark, "gold.dim_customer_scd2")
cur = dim.toDF().filter("is_current = true")

src = (spark.read.parquet("/landing/customers")                      # one row per customer_id!
         .withColumn("row_hash", F.sha2(F.concat_ws("||", "name", "email", "city"), 256))
         .withColumn("load_ts", F.current_timestamp()))

# 1) Only new customers or customers whose tracked attributes changed
changed = (src.alias("s")
             .join(cur.alias("t"), "customer_id", "left")
             .filter("t.row_hash IS NULL OR s.row_hash <> t.row_hash")
             .select("s.*"))

# 2) Two copies of each changed row:
#    - merge_key = business key  -> MATCHES the open row  -> will CLOSE it
#    - merge_key = NULL          -> matches nothing        -> will INSERT the new version
to_close = (changed.join(cur.select("customer_id"), "customer_id", "left_semi")   # only if an open row exists
                   .withColumn("merge_key", F.col("customer_id")))
to_insert = changed.withColumn("merge_key", F.lit(None).cast("bigint"))
staged = to_close.unionByName(to_insert)

# 3) Apply
(dim.alias("t")
   .merge(staged.alias("s"), "t.customer_id = s.merge_key AND t.is_current = true")
   .whenMatchedUpdate(set={
        "is_current":   "false",
        "effective_to": "s.load_ts"})
   .whenNotMatchedInsert(values={
        "customer_id":    "s.customer_id",
        "name":           "s.name",
        "email":          "s.email",
        "city":           "s.city",
        "row_hash":       "s.row_hash",
        "effective_from": "s.load_ts",
        "effective_to":   "NULL",
        "is_current":     "true"})
   .execute())

Querying SCD2

-- Current state
SELECT * FROM gold.dim_customer_scd2 WHERE is_current = true;

-- Point-in-time ("as of") join from a fact table
SELECT f.order_id, f.order_ts, d.city
FROM silver.orders f

Pitfalls
  • Source must have one row per business key per run – dedupe first, or multiple changes in one batch need ordered processing.
  • Pick the tracked columns deliberately (the row_hash input). Tracking noisy columns creates endless versions.
  • Use the source's change timestamp for effective_from when available, not the load time, so history is accurate when jobs are re-run.
  • Keep the job idempotent: re-running the same batch must not create duplicate versions (the hash comparison guarantees this).
  • In Databricks, APPLY CHANGES INTO ... STORED AS SCD TYPE 2 (Delta Live Tables) does all this declaratively.

A streaming DataFrame is an unbounded table; the same DataFrame API applies. Progress is tracked in a checkpoint directory, which gives restartability and exactly-once semantics with idempotent/transactional sinks like Delta.

9.1Data Quality Checks

def run_dq(df, key_cols, required_cols, min_rows=1):
    problems = []
    total = df.count()
    if total < min_rows:
        problems.append(f"row count {total} < {min_rows}")

    # nulls in required columns
    null_counts = df.select([F.sum(F.col(c).isNull().cast("int")).alias(c) for c in required_cols]).first().asDict()
    problems += [f"{c}: {n} nulls" for c, n in null_counts.items() if n]

    # duplicate keys
    dups = df.groupBy(*key_cols).count().filter("count > 1").count()
    if dups:
        problems.append(f"{dups} duplicate keys on {key_cols}")

    # range / domain rules
    bad = df.filter("amount < 0 OR status NOT IN ('NEW','OPEN','CLOSED')").count()
    if bad:
        problems.append(f"{bad} rows violate business rules")

    if problems:
        raise ValueError("Data quality failed: " + "; ".join(problems))
    return total

run_dq(clean_df, ["order_id"], ["order_id", "cust_id", "amount"])

bad  = df.exceptAll(good).withColumn("_rejected_at", F.current_timestamp())
bad.write.mode("append").format("delta").saveAsTable("quarantine.orders")
TipEach count() is a full job. Compute all metrics in one agg and cache() the DataFrame if you run several checks. Delta CHECK constraints (ALTER TABLE t ADD CONSTRAINT c CHECK (amount >= 0)) enforce rules at write time.

Spark UI cheat sheet

  • Jobs / Stages: which stage is slow? Compare task duration min/median/max.
  • SQL tab: visual plan with row counts per operator – spot an exploding join.
  • Storage tab: verify caches exist and fit in memory.
  • Executors tab: GC time > 10% of task time signals memory pressure.

AProduction Checklist & Cheat Sheet

  • ✅ Explicit schemas; Parquet/Delta over CSV/JSON after ingestion.
  • ✅ Filter/select early; check explain() for pushed filters and join strategy.
  • ✅ Broadcast small dimensions; enable AQE and skew-join handling.
  • ✅ Right-size spark.sql.shuffle.partitions; avoid tiny output files.
  • ✅ Prefer built-in functions > pandas_udf > Python UDF.
  • ✅ Cache only reused data; always unpersist().
  • ✅ Make jobs idempotent (dynamic partition overwrite or Delta MERGE).
  • ✅ Never collect() unbounded data; add data-quality checks (null counts, row counts) between stages.
