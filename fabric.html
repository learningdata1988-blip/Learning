1What is Microsoft Fabric?

Microsoft Fabric is a unified, SaaS analytics platform that brings data integration, data engineering, data warehousing, data science, real-time analytics and business intelligence (Power BI) into one product. All workloads share one storage layer (OneLake), one capacity-based billing model, one security/governance model (Microsoft Purview) and one UI.

1.1OneLake, Shortcuts & Mirroring

  • OneLake is automatically provisioned per tenant – one logical lake built on ADLS Gen2, with an ADLS-compatible API (DFS endpoint) so existing tools work.
  • Hierarchy: Tenant → Workspace → Item (Lakehouse/Warehouse…) → Tables/Files.
  • Default format for tables is Delta Lake (Parquet + transaction log).
abfss://<workspace>@onelake.dfs.fabric.microsoft.com/<lakehouse>.Lakehouse/Tables/orders
abfss://<workspace>@onelake.dfs.fabric.microsoft.com/<lakehouse>.Lakehouse/Files/raw/2026/10/orders.csv
https://onelake.dfs.fabric.microsoft.com/<workspace>/<lakehouse>.Lakehouse/Files/...   (ADLS Gen2 REST)

Shortcuts – reference data without copying

A shortcut is a pointer in a Lakehouse (or KQL database) to data elsewhere: another Fabric item/workspace, ADLS Gen2, Amazon S3, S3-compatible, Google Cloud Storage, Dataverse, and more. It appears as a folder/table; reads go to the source (cached optionally).

  • Shortcut under Tables/ pointing to a Delta folder → shows up as a queryable table.
  • Shortcut under Files/ → any file format, raw access.
  • Deleting a shortcut does not delete source data (but deleting data through a shortcut path may affect the target depending on permissions).

Mirroring

Continuously replicates an operational database into OneLake as Delta tables with no ETL (supported sources include Azure SQL Database, Azure Cosmos DB, Snowflake, and others, with the list growing). Replication compute is free of capacity charge; query/transform compute is not. Use when you need analytics on operational data with minimal latency and no pipeline maintenance.

1.2Capacity, Licensing & Workspaces

  • Capacity = pool of compute (Capacity Units, CU) purchased as an Azure F SKU (F2, F4, F8 … F2048) or Trial. All workloads draw from the same pool, which is shared by every workspace assigned to the capacity.
  • F2–F32 and smaller SKUs can be paused/resumed and scaled in Azure; Power BI content consumers on SKUs below F64 need Power BI Pro/PPU licenses, while F64+ allows free viewers.
  • Bursting and smoothing: short spikes are allowed and averaged over time (background operations smoothed over 24 hours, interactive over a short window); sustained overuse leads to throttling (delays → rejection).
  • Monitor with the Fabric Capacity Metrics app; reduce cost by pausing dev capacities, right-sizing, optimizing heavy jobs and scheduling off-peak.

2Lakehouse

A Lakehouse combines the flexibility of a data lake (any file) with the structure of a warehouse (Delta tables). Creating one produces three artifacts automatically: the Lakehouse itself, a SQL analytics endpoint and a default semantic model.

AreaContainsNotes
Tables/Managed Delta tables (and shortcut tables)Auto-discovered by the SQL endpoint; use for curated data
Files/Unmanaged files: CSV, JSON, Parquet, images…Landing zone / bronze raw files; not exposed to SQL endpoint
SQL analytics endpointRead-only T-SQL over Delta tablesViews, functions, procedures allowed; no INSERT/UPDATE on tables
Schemas (optional)Organize tables as schema.tableEnable at Lakehouse creation (e.g. bronze, silver)
SQL endpoint syncThe SQL endpoint picks up new/changed Delta tables with a short metadata sync delay. If a table just written by Spark isn't visible, wait or trigger a refresh of the endpoint metadata.
Table namingAvoid spaces and special characters in table/column names – they cause problems in the SQL endpoint and downstream tools. Delta features such as column mapping need care when enabled.

2.1Notebooks & Spark in Fabric

Fabric runs Apache Spark with Starter pools (pre-warmed, sessions start in seconds) and custom pools; Environments hold libraries and Spark properties. A default Lakehouse can be attached to a notebook so relative paths (Files/..., Tables/...) and table names resolve automatically.

# ---- Read raw files from the attached Lakehouse (relative path) ----
raw = (spark.read.option("header", True).option("inferSchema", True)
         .csv("Files/raw/orders/*.csv"))

# ---- Write a managed Delta table (shows up under Tables/) ----
(raw.write.format("delta").mode("overwrite")
    .option("overwriteSchema", "true")
    .saveAsTable("bronze_orders"))                  # with schemas enabled: "bronze.orders"

# ---- Read it back via name or SQL ----
df = spark.read.table("bronze_orders")
spark.sql("SELECT COUNT(*) AS n FROM bronze_orders").show()

# ---- Absolute OneLake path (works across workspaces/lakehouses) ----
path = "abfss://MyWorkspace@onelake.dfs.fabric.microsoft.com/Sales.Lakehouse/Tables/orders"
other = spark.read.format("delta").load(path)

# ---- Write files (e.g. export) ----
df.write.mode("overwrite").parquet("Files/exports/orders_parquet")

Upsert with Delta MERGE

from delta.tables import DeltaTable
from pyspark.sql import functions as F, Window

updates = (spark.read.table("bronze_orders")
             .filter(F.col("ingest_date") == run_date))
w = Window.partitionBy("order_id").orderBy(F.col("updated_at").desc())
updates = updates.withColumn("rn", F.row_number().over(w)).filter("rn = 1").drop("rn")

tgt = DeltaTable.forName(spark, "silver_orders")
(tgt.alias("t").merge(updates.alias("s"), "t.order_id = s.order_id")
    .whenMatchedUpdateAll(condition="s.updated_at > t.updated_at")
    .whenNotMatchedInsertAll()
    .execute())
TipsUse High-concurrency mode to share one Spark session across notebooks (cheaper and faster to start). Enable the Native Execution Engine (Velox/Gluten based) in the Environment for faster Spark SQL/DataFrame processing on supported operations. Keep spark.sql.shuffle.partitions and AQE settings tuned as on any Spark platform.

2.2Delta Tables, V-Order & Maintenance

  • V-Order: a Microsoft write-time Parquet optimization (sorting/encoding/compression) that makes reads faster across Fabric engines (especially Power BI Direct Lake and SQL endpoint). Enabled by default for some workloads; may slightly slow writes – consider disabling in write-heavy bronze layers.
  • Small-file problem: many tiny files hurt read performance; compact them regularly.
  • Optimize Write and auto-compaction settings reduce small files at write time.
-- Spark SQL in a notebook
OPTIMIZE silver_orders;                                 -- compact small files
OPTIMIZE silver_orders VORDER;                          -- compact + apply V-Order
OPTIMIZE silver_orders ZORDER BY (customer_id);         -- co-locate by column for faster filters
VACUUM silver_orders RETAIN 168 HOURS;                  -- remove unreferenced files (default 7 days)
DESCRIBE HISTORY silver_orders;                         -- audit / time travel
SELECT * FROM silver_orders VERSION AS OF 5;
RESTORE TABLE silver_orders TO VERSION AS OF 5;
# Session-level Spark settings (examples – verify exact names for your runtime)
spark.conf.set("spark.sql.parquet.vorder.default", "true")           # V-Order on writes
spark.conf.set("spark.microsoft.delta.optimizeWrite.enabled", "true")
spark.conf.set("spark.sql.adaptive.enabled", "true")

The Lakehouse UI also offers Table maintenance (right-click a table → Maintenance) to run OPTIMIZE (with V-Order / Z-Order) and VACUUM without code.

3Fabric Warehouse (T-SQL)

The Warehouse is a fully transactional, scale-out relational warehouse with a T-SQL surface area. Data is stored as Delta/Parquet in OneLake; compute is serverless and separated from storage. Multi-table transactions and snapshot isolation are supported.

-- Create schema and table
CREATE SCHEMA gold;
GO
CREATE TABLE gold.dim_customer (
    customer_key  BIGINT        NOT NULL,
    customer_id   INT           NOT NULL,
    name          VARCHAR(100)  NULL,
    city          VARCHAR(100)  NULL
);                                              -- no IDENTITY in older builds; check current docs. Constraints are NOT ENFORCED

-- Load: CTAS from a Lakehouse table in the same workspace (cross-database query)
CREATE TABLE gold.fact_orders
AS
SELECT o.order_id, o.customer_id, CAST(o.order_date AS DATE) AS order_date, o.amount
FROM   SalesLakehouse.dbo.silver_orders AS o       -- three-part name: item.schema.table
WHERE  o.status = 'DONE';

-- Bulk load files from storage
COPY INTO gold.stage_orders
FROM 'https://account.dfs.core.windows.net/container/orders/*.parquet'
WITH (FILE_TYPE = 'PARQUET');

-- Regular DML
INSERT INTO gold.dim_customer (customer_key, customer_id, name, city)
SELECT ROW_NUMBER() OVER (ORDER BY customer_id), customer_id, name, city FROM SalesLakehouse.dbo.silver_customers;

UPDATE gold.dim_customer SET city = 'Mumbai' WHERE customer_id = 101;
DELETE FROM gold.fact_orders WHERE order_date < '2020-01-01';

-- Views, stored procedures
CREATE VIEW gold.v_monthly_sales AS
SELECT DATETRUNC(month, order_date) AS month, SUM(amount) AS revenue
FROM gold.fact_orders GROUP BY DATETRUNC(month, order_date);
GO
CREATE PROCEDURE gold.usp_refresh_fact_orders AS
BEGIN
    SET NOCOUNT ON;
    BEGIN TRAN;
        TRUNCATE TABLE gold.fact_orders;
        INSERT INTO gold.fact_orders SELECT order_id, customer_id, order_date, amount FROM SalesLakehouse.dbo.silver_orders;
    COMMIT;
END;
Warehouse features
  • Cross-database queries across Warehouses and Lakehouse SQL endpoints in the same workspace (three-part names).
  • Zero-copy clone (CREATE TABLE … AS CLONE OF …) and time travel (OPTION (FOR TIMESTAMP AS OF …)) via Delta metadata.
  • Automatic statistics and query insights views for monitoring; no manual indexing or distribution keys to manage.
  • T-SQL support is a subset of SQL Server – some features (e.g. certain data types, triggers, cursors) are unavailable or differ; check the current surface-area documentation.

Typical metadata-driven pattern

  1. Lookup reads a control table (source table, target table, load type, watermark column).
  2. ForEach iterates over rows (set batch count for parallelism).
  3. Inside: Copy data with a parameterized query (WHERE modified > @{item().last_watermark}) into the Lakehouse.
  4. Notebook merges into silver; Script updates the watermark.
  5. On failure path: Teams/Outlook activity + log to an audit table.

Triggers: schedule trigger, tumbling-style via schedule parameters, event triggers (e.g. file arrival in OneLake/storage via Activator/Real-Time hub). Set retry count / timeout on each activity and use On fail / On completion dependency paths for error handling.

4.1Dataflows Gen2

  • Low-code Power Query (M) transformations with a visual editor; good for analysts and light-to-medium ETL.
  • Each query can set a data destination (Lakehouse table, Warehouse, Azure SQL, etc.) with append/replace.
  • Run on demand, on a schedule, or as a pipeline activity; supports incremental refresh for supported sources and staging via Lakehouse for performance.
  • Use Dataflows for self-service and quick wins; use Spark notebooks for large volumes, complex logic, and code reuse/testing.

4.2Incremental Load (Watermark) Pattern

# Notebook: incremental load from bronze to silver using a watermark table
from pyspark.sql import functions as F
from delta.tables import DeltaTable

wm_tbl = "ctl_watermark"
last_wm = (spark.read.table(wm_tbl).filter("table_name = 'orders'")
             .select("last_value").first()["last_value"])            # e.g. '2026-10-29 23:59:59'

src = spark.read.table("bronze_orders").filter(F.col("modified_at") > F.lit(last_wm))

if src.limit(1).count() > 0:
    new_wm = src.agg(F.max("modified_at")).first()[0]

    (DeltaTable.forName(spark, "silver_orders").alias("t")
        .merge(src.dropDuplicates(["order_id"]).alias("s"), "t.order_id = s.order_id")
        .whenMatchedUpdateAll().whenNotMatchedInsertAll().execute())

    spark.sql(f"UPDATE {wm_tbl} SET last_value = '{new_wm}' WHERE table_name = 'orders'")   # advance only after success
notebookutils.notebook.exit(f"rows={src.count()}")
Best practicesAdvance the watermark after a successful merge, make loads idempotent (merge, not blind append), handle late data with an overlap window, and log run metadata (rows, duration, status) to an audit table.

5.1Power BI & Direct Lake

6Medallion Architecture End-to-End

Sources ──► Pipeline Copy / Mirroring / Shortcuts │ BRONZE (Lakehouse) raw, append-only, as-is (Files/ + Delta) │ Notebook: clean, dedupe, type-cast, conform SILVER (Lakehouse) validated, deduplicated Delta tables │ Notebook / T-SQL: joins, aggregates, star schema GOLD (Warehouse or Lakehouse) business-ready facts & dimensions │ Semantic model (Direct Lake) ──► Power BI reports / Copilot / Data Agents
# Bronze: ingest as-is with audit columns
from pyspark.sql import functions as F
bronze = (spark.read.option("header", True).csv("Files/landing/orders/")
            .withColumn("_ingest_ts", F.current_timestamp())
            .withColumn("_source_file", F.input_file_name()))
bronze.write.format("delta").mode("append").saveAsTable("bronze.orders")

# Silver: clean + conform + dedupe
silver = (spark.read.table("bronze.orders")
            .withColumn("order_date", F.to_date("order_date"))
            .withColumn("amount", F.col("amount").cast("decimal(18,2)"))
            .filter("order_id IS NOT NULL AND amount >= 0")
            .dropDuplicates(["order_id"]))
silver.write.format("delta").mode("overwrite").saveAsTable("silver.orders")

# Gold: aggregate for reporting
gold = (spark.read.table("silver.orders").groupBy("order_date")
          .agg(F.sum("amount").alias("revenue"), F.countDistinct("customer_id").alias("customers")))
gold.write.format("delta").mode("overwrite").saveAsTable("gold.daily_sales")
OrchestrationOne pipeline: Copy/Mirror → Notebook(bronze→silver) → Notebook or Warehouse procedure (silver→gold) → refresh semantic model → notify. Parameterize by environment and date.

7Interview Questions & Answers

What is Microsoft Fabric and how is it different from Azure Synapse?
Fabric is a unified SaaS analytics platform (data integration, engineering, warehousing, real-time, science and Power BI) on one storage layer, OneLake, with capacity-based billing. Synapse is a PaaS collection of separate services (dedicated/serverless SQL pools, Spark pools, pipelines) you provision and manage individually. Fabric removes most infrastructure setup and shares data across workloads without copies.
What is OneLake?
The single, tenant-wide logical data lake built on ADLS Gen2 that stores all Fabric data in open Delta/Parquet format. It's organized by workspace and item, exposes an ADLS-compatible API, and avoids data silos and duplication.
What are shortcuts and when would you use them?
Pointers to data in other Fabric items or external storage (ADLS Gen2, S3, GCS, Dataverse…) that appear as folders/tables in a Lakehouse without copying data. Use them to reuse shared datasets across workspaces, to access data in place, and to avoid duplicate pipelines.
What is mirroring?
Continuous, near-real-time replication of an operational database (e.g. Azure SQL, Cosmos DB, Snowflake) into OneLake as Delta tables, requiring no ETL pipelines. It enables analytics on operational data with minimal latency.
Lakehouse vs Warehouse – when do you choose each?
Lakehouse: Spark/Python skills, mixed structured and unstructured data, bronze/silver layers, ML. Warehouse: T-SQL skills, full DML/DDL, multi-table transactions, gold/serving layer and dimensional models. Both store Delta in OneLake and can be queried together via cross-database queries.
What is the SQL analytics endpoint?
An automatically created, read-only T-SQL endpoint over a Lakehouse's Delta tables. You can run SELECT queries and create views/functions/procedures, but can't INSERT/UPDATE tables – writes happen via Spark or pipelines.
What is Direct Lake?
A Power BI storage mode where the semantic model reads Delta/Parquet files directly from OneLake into memory on demand – import-like performance without a data copy and without querying a source at runtime. It requires well-maintained Delta tables; unsupported scenarios can fall back to DirectQuery.
Explain Fabric capacity, bursting, smoothing and throttling.
Capacity is the pool of compute (CUs) bought as an F SKU shared by all workloads. Bursting lets jobs temporarily use more than the purchased CUs; smoothing spreads that consumption over time (longer for background jobs). If sustained usage exceeds capacity, Fabric throttles – first delaying, then rejecting operations. Monitor with the Capacity Metrics app.
What is V-Order?
A write-time optimization of Parquet files (special sorting, row-group distribution, dictionary encoding and compression) that improves read performance for Fabric engines – notably Power BI Direct Lake, the SQL endpoint and Spark. It can add a little write overhead, so use it mainly for read-heavy layers.
How do you implement incremental loading in Fabric?
Use a watermark (last modified timestamp or ID) stored in a control table. A pipeline Lookup reads it, Copy data or a notebook extracts only newer rows, a Delta MERGE upserts them idempotently into silver, and the watermark is advanced after success. Alternatives: mirroring, Dataflow Gen2 incremental refresh, Delta Change Data Feed for downstream propagation.
Pipelines vs Dataflows Gen2 vs Notebooks?
Pipelines orchestrate and copy data at scale. Dataflows Gen2 provide low-code Power Query transformations for analysts. Notebooks give full code control (Spark) for heavy, complex, testable transformations. They are often combined: a pipeline orchestrates notebooks and dataflows.
How do you pass parameters between a pipeline and a notebook?
Mark a cell as the parameter cell in the notebook; the pipeline's Notebook activity supplies base parameters that override those values. The notebook returns a value with notebookutils.notebook.exit(), which the pipeline reads from @activity('Notebook1').output.result.exitValue.
How do you secure data in Fabric?
Layered: Entra ID and Conditional Access, workspace roles, item-level permissions, SQL GRANT/DENY with row-level and column-level security and dynamic masking, OneLake data access roles, RLS/OLS in semantic models, sensitivity labels and lineage via Purview, secrets in Key Vault, and private links for network isolation.
How would you implement CI/CD in Fabric?
Connect workspaces to Git (Azure DevOps/GitHub) for version control and branching, use deployment pipelines (Dev→Test→Prod) with deployment rules for environment-specific settings, and automate with REST APIs, GitHub Actions/Azure DevOps and the fabric-cicd library. Parameterize workspace/lakehouse references.
How do you handle the small-files problem?
Enable Optimize Write, run OPTIMIZE (with V-Order as needed) on a schedule or via Lakehouse table maintenance, avoid over-partitioning, batch streaming writes with larger triggers, and VACUUM old files after the retention period.
What is Real-Time Intelligence?
The Fabric workload for streaming and event-driven analytics: Eventstreams ingest and route events, Eventhouses (KQL databases) store and query time-series data fast with KQL, Real-Time Dashboards visualize it, and Activator triggers actions on conditions.
How do you design a medallion architecture in Fabric?
Bronze Lakehouse for raw append-only ingestion (via pipelines, mirroring, shortcuts); silver Lakehouse for cleaned, deduplicated, conformed Delta tables built by notebooks; gold Warehouse or Lakehouse with star-schema facts/dimensions; Direct Lake semantic model on top. Orchestrate with pipelines, separate workspaces per layer/environment, and secure per layer.
How do you upsert data in Fabric?
In Spark notebooks use Delta MERGE (DeltaTable.merge or SQL MERGE INTO) after deduplicating the source. In a Warehouse use T-SQL DML (INSERT/UPDATE/DELETE, or MERGE where supported) inside a transaction. For SCD2, close the current row and insert a new version using a staged merge.
What is a Fabric Environment?
A reusable configuration item bundling Spark runtime version, compute settings, libraries (public/custom wheels) and Spark properties that can be attached to notebooks and Spark job definitions to ensure consistency across teams and stages.
How do you monitor and troubleshoot failures?
Use the Monitoring hub for run status and history, drill into the Spark UI / History Server and driver/executor logs for notebook failures, check pipeline activity input/output in run details, review Capacity Metrics for throttling, and add alerts (Teams/Outlook activities, Activator, Azure Monitor).
Can Spark write to a Fabric Warehouse?
Not directly as a standard Spark table sink – Warehouse tables are managed through T-SQL (and pipelines/dataflows/COPY INTO). Spark can read Warehouse Delta data and Lakehouse tables can be exposed to the Warehouse via cross-database queries or shortcuts; a Spark connector for Warehouse reads/writes also exists in newer runtimes – verify current support.
